# GeWu 核心概念定义

> 本文档记录 GeWu 项目中核心概念的定义和讨论结果。
>
> **流程**：讨论中 → 已确定 → 输出到相关 `agents.md` 指导开发。
> 发现实现与文档冲突时，应中断并展开讨论。
>
> **最后更新**：2026-07-12

---

## 核心理念

我们管理的是用户的知识资产，包括文档、笔记、表格、图片以及各类附件。我们希望在设计上比普通文件管理器更有语义，但又不牺牲文件的开放性和可迁移性。

**基础设计原则：**
- 文件系统依然是真实存储，任何更改都能被同步、备份，甚至用其他编辑器查看。
- 我们的软件通过**约定**赋予特定文件夹更强的意义：项目、包。
- 提供简单的"文件夹即整体"的操作体验，同时支持内容级别的灵活组合与复用。

---

## 概念层次

```
库 (Library)
  └── 项目 (Project)    —— 主题聚合容器（可选）
        └── 包 (Package) —— 内容不可分割的最小完整单元
              ├── 片段 (Fragment)    —— 包内可按顺序组合的内容块
              ├── 附件 (Attachment)  —— 包私有的二进制文件
              └── 格式变体 (Variant) —— 导出的派生格式（pdf/docx等）
```

| 概念 | 本质 | 物理形态 | 状态 |
|------|------|----------|------|
| 库 | 知识库的顶层容器 | 一个根目录 + SQLite 数据库 | ✅ 已实现 |
| 项目 | 主题聚合的容器（可选） | `.proj` 后缀文件夹 | 🟡 Phase 1 |
| 包 | 内容不可分割的完整单元 | `.pack` 后缀文件夹 | 🟡 Phase 1 |
| 片段 | 包内可组合的内容块 | 片段文件（.md/.csv/.code 等） | 🟡 Phase 2 |
| 附件 | 包私有的二进制文件 | `attachments/` 目录下 | 🟡 Phase 1 |
| 格式变体 | 导出的派生格式 | `exports/` 目录下 | 🟡 Phase 3 |

## 库（Library）

**状态**：✅ 已实现

### 定义

一个库 = **一个主页（库根）+ 一组注册文件夹**。库根是一个普通文件夹（如 `D:\知识库`），记录着各注册文件夹的位置；注册文件夹可位于**磁盘任意位置**（不需要在库根内），通过 `.gewu/folder.json` 身份文件标识（v7 文件夹自治，2026-08-07，见 [folder-autonomy-spec](../packages/docs/folder-autonomy-spec.md)）。

库的元数据存储在库根 `.gewu/kmgr.db`（全局单库）。库之间完全独立，无跨库引用。

> ⚠️ 旧文档曾将"库"定义为"一个根目录 + 数据库"，且包/文件夹必须位于库根内。0.26 起已重新定位：**库根只是主页（索引区），内容都在注册文件夹里**。详见本文件「库内（判定）」。

### 职责

- 管理知识库的元数据（名称、路径、创建时间）
- 维护注册文件夹清单（位置、身份、类型）
- 提供文件索引和全文搜索
- 提供双链索引、共享片段、共享资源的管理

### 库根（主页）

库根是**纯索引区**，只承载系统内容：

- `.gewu/` — 系统配置 + `kmgr.db` + 备份（`backup-<时间戳>/`）
- `.shared/` — 库级共享资源池（系统托管，见下文）
- **不存放用户文件**。库根内散落的旧数据属于迁移期遗留，UI 显示「待整理内容」引导归入文件夹；库根**内部禁止注册文件夹**（注册被拒绝）。

### 注册文件夹

- 可位于磁盘任意位置（库根外任意路径；库根内拒绝注册）
- 每个文件夹含 `.gewu/folder.json` 身份文件（folder_uuid），应用外移动后仅需「重新定位」
- 类型：工作区 / 归档 / 通用 / 收件箱 / 资源
- 文件夹内的内容（.pack / 文件）通过扫描注册进库

### 库内（判定）★核心规则

> **库内 = 任一注册文件夹内（含收件箱）。库根不承载用户内容，故不属于「库内」内容区。**

- 内容归属（包归属、扫描、自动索引）：以「在任一注册文件夹内」为基准，由后端 `classify_path` 命令判定
- 打开体验（是否弹「导入知识库」框）：采用**宽口径** = 注册文件夹 ∪ 库根物理内（库根散落旧文件也直接打开，不弹框）
- 代码中一律使用后端命令判定，**禁止**前端用 `isPathInside(kbRoot, path)` 自行前缀匹配（会导致库根外注册文件夹内的文件被误判为「库外」）

### 物理结构

```
我的工作空间/                 ← 库根（主页，纯索引区）
  .gewu/
    kmgr.db                  ← SQLite 全局单库（隐藏）
    backup-20260808-xxxx/    ← 备份
  .shared/                   ← 库级共享资源池（系统托管）
  [文件夹清单]               ← 纯逻辑指针，不物理存储

D:\docs\工作区/              ← 注册文件夹（磁盘任意位置）
  .gewu/folder.json          ← 文件夹身份
  游记.pack/                 ← 包（归属该文件夹）
  ...
D:\收件箱/                   ← 收件箱类型注册文件夹
  ...
```

### 当前实现

`kmgr-core` 中的 `knowledge_bases` 表（库根）+ `library_folders` 表（注册文件夹），通过 `plugin-library-manager` 插件管理 CRUD。

## 项目（Project）

**状态**：🟡 Phase 1（基本标识） / Phase 4（聚合视图）

### 定义

项目是**可选的**主题聚合容器，方便用户分组管理相关的包。

### 物理结构

```
设计案例.proj/           ← 项目文件夹（.proj 后缀）
  .projmeta.json         ← 项目元数据（隐藏）
  A公司品牌升级.pack/     ← 包
  B公司宣传册.pack/       ← 包
  项目 notes.md          ← 普通文件
```

### 元数据 `.projmeta.json`

```json
{
  "id": "项目UUID",
  "title": "设计案例",
  "color": "#3b82f6",
  "icon": "🎨",
  "description": "2026 年的设计案例集合",
  "tags": ["设计", "客户案例"]
}
```

### 聚合视图（Phase 4）

项目提供聚合视图：看板、时间线、标签云。

### 场景

> 小李是一名自由职业设计师。他为不同年份的设计案例创建了项目 `2026设计案例.proj`、`2025设计案例.proj`，每个项目内包含对应年份的客户案例包。在项目看板视图中，他可以按状态（进行中/已完成/归档）拖拽排列所有包。

### 与文件夹的区别

| | 普通文件夹 | 项目 |
|---|---|---|
| 标识 | 无特殊标识 | `.proj` 后缀 + `.projmeta.json` |
| 元数据 | 无 | 名称/颜色/图标/描述/标签 |
| 聚合视图 | 无 | 看板/时间线/标签云 |

⚠️ **风险点**：用户可以直接在文件管理器中重命名/删除 `.proj` 文件夹。软件需要通过数据库检测并处理这种情况（标记为"项目缺失"）。

## 包（Package）

**状态**：🟡 Phase 1

### 定义

包是内容的最小完整单元，也是移动、复制、删除、分享的最小粒度。包内的文件互相依赖，拆开后不完整。

### 物理结构

**简单模式（默认，用户无感知片段概念）：**

```
游记.pack/               ← 包文件夹（.pack 后缀）
  .packmeta.json         ← 包元数据（隐藏）
  游记.md                ← 唯一片段（文件名由用户指定）
  attachments/           ← 附件目录
    DSC001.jpg
  exports/               ← 导出目录（可选）
    游记.pdf
```

**多片段模式（用户主动拆分后）：**

```
项目复盘.pack/
  .packmeta.json
  fragments/             ← 片段目录
    背景介绍.md
    数据表.csv
    结论总结.md
  attachments/
    chart.png
  exports/
    项目复盘.pdf
```

### 元数据 `.packmeta.json`

```json
{
  "id": "包UUID",
  "title": "游记",
  "fragments": [
    {"id": "frag1", "type": "markdown", "file": "游记.md"}
  ],
  "shared_refs": [],
  "resources": [],
  "exports": {
    "pdf": {
      "file": "exports/游记.pdf",
      "stale": true,
      "converter": "pandoc",
      "template": "exports/templates/pdf.tex",
      "script": "exports/export-pdf.sh"
    }
  }
}
```

多片段模式示例：

```json
{
  "id": "包UUID",
  "title": "项目复盘",
  "fragments": [
    {"id": "frag1", "type": "markdown", "file": "fragments/背景介绍.md"},
    {"id": "frag2", "type": "csv", "file": "fragments/数据表.csv"},
    {"id": "frag3", "type": "markdown", "file": "fragments/结论总结.md"}
  ],
  "shared_refs": [],
  "resources": []
}
```

### 核心特征

1. **内容完整性**：包内文件互相依赖，拆开后各自不完整
2. **原子性**：移动/复制/删除时整体操作
3. **双链目标**：`[[包名]]` 链接到包，无论内部结构如何变化，链接都稳定

### 文件名规则

- **简单模式**：文件名由用户指定（如 `游记.md`），不强制为 `index.md`
  - 避免文件系统中出现大量同名 `index.md`
  - 全局搜索、最近打开列表中更易区分
- **多片段模式**：片段文件放在 `fragments/` 目录下，文件名可读（如 `背景介绍.md`）
  - 片段 ID（`frag1`、`frag2`）在 `.packmeta.json` 中保持稳定，用于排序和引用
  - 重命名片段文件时，软件同步更新 `.packmeta.json` 中的 `file` 字段

### 场景

> 小李写了一篇游记，包含文字和照片。他将文字保存为 `游记.md`，照片放在 `attachments/` 中。这个包是完整的——如果拆开，照片离开了文字 context 就失去了意义。当小李把 `游记.pack/` 发送给朋友时，朋友收到的是完整的游记内容。

### 与项目的区别

| | 包 | 项目 |
|---|---|---|
| **文件关系** | 互相依赖，拆开不完整 | 相互独立，因主题而聚 |
| **示例** | 一篇文章 + 内嵌图片 | "我的博客"含多篇文章 |
| **操作粒度** | 整体操作 | 可单独操作其中包 |

⚠️ **风险点**：用户在文件管理器中直接移动包内的文件（如把 `attachments/` 中的图片移到包根目录），会导致 `.packmeta.json` 中的引用断裂。软件需要通过库健康检查检测并修复。

## 片段（Fragment）

**状态**：🟡 Phase 2

### 定义

片段是包内可按顺序组合的内容块。一个包可以包含一个或多个片段，在界面上拼接展示为一个完整文档。

### 片段类型

| 类型 | 文件后缀 | 说明 |
|------|----------|------|
| Markdown | `.md` | 富文本内容 |
| CSV 表格 | `.csv` | 表格数据 |
| 代码块 | `.code` | 代码片段（可指定语言） |
| 图片 | `.png` / `.jpg` | 显示用图片（区别于附件） |

### 编辑体验

- 每个片段独立编辑，通过 UI 组件竖向按顺序拼接
- 用户体验上类似于一个长文档编辑
- 片段显示顺序由 `.packmeta.json` 的 `fragments` 数组决定
- 拖动排序时只改变数组顺序，不改变文件名

### 场景

> 小李在做一个项目复盘，内容包含：背景介绍（Markdown）、数据表（CSV）、结论总结（Markdown）。他将这三部分分别作为片段，在编辑器中它们竖向拼接展示为一个完整文档。当他需要调整顺序时，只需拖拽片段排序，不影响文件内容。

⚠️ **风险点**：片段间的光标流动（从片段 A 末尾按 Down 跳到片段 B 开头）需要编辑器组件间协调。初期可以不支持跨片段光标流动，作为 Phase 2 优化项。

## 附件（Attachment）

**状态**：🟡 Phase 1

### 定义

包内私有的二进制文件，放在 `attachments/` 目录下，仅供本包使用。

### 与共享资源的区别

| | 附件 | 共享资源 |
|---|---|---|
| 位置 | 包内 `attachments/` | 库级 `.shared/` |
| 归属 | 包私有 | 库级共享 |
| 复用 | 仅本包 | 多包引用 |

若需多包共享二进制文件，使用库级共享资源（见下文）。

## 格式变体（Variant）

**状态**：🟡 Phase 3

### 定义

从包内容导出的 PDF、DOCX 等文件，放在 `exports/` 目录中。它们不属于包的完整性范围，可随时删除并重新生成。

### 同步策略

**stale 标记 + 手动刷新**：

1. 源文件（片段）修改后，所有格式变体标记为 `stale: true`
2. 用户在 UI 上看到"格式变体已过期"提示
3. 用户主动触发重新导出，生成新的格式变体
4. 避免实时转换的性能开销

### 导出配置

`.packmeta.json` 的 `exports` 字段记录导出配置：

```json
{
  "exports": {
    "pdf": {
      "file": "exports/游记.pdf",
      "stale": true,
      "converter": "pandoc",
      "template": "exports/templates/pdf.tex",
      "script": "exports/export-pdf.sh"
    }
  }
}
```

- `converter`：转换工具（pandoc / docx-js / exceljs 等）
- `template`：模板文件路径（可选）
- `script`：导出脚本路径（可选）

### 场景

> 小李将游记导出为 PDF 发给朋友。几天后他修改了游记内容，PDF 标记为 stale。他看到"格式变体已过期"提示后，点击"重新导出"，生成新的 PDF。

⚠️ **风险点**：用户在文件管理器中直接修改导出文件，软件无法检测。stale 标记仅反映源文件变更，不反映导出文件被外部修改。

## 共享片段机制

**状态**：🟡 Phase 3

### 场景

> 小李写了一份"合同通用条款"，希望未来的多份合同都能引用同一段内容。当通用条款更新时，所有引用的合同都能看到最新版（或锁定某个历史版本）。

### 发布与引用流程

1. **发布为共享片段**：在包内选中一段文本/表格，右键"发布为共享片段"。内容存为独立片段文件，在数据库 `shared_fragments` 表中注册，保存初始版本。
2. **在其他包中引用**：编辑其他包时，输入 `[[` 或点击"插入共享块"，搜索找到该片段，确认后目标包的 `.packmeta.json` 的 `shared_refs` 中增加一条引用记录。
3. **查看与更新**：引用处实时显示共享片段的最新内容（默认跟随最新版本）。源片段修改后，引用方看到更新；用户也可"锁定到当前版本"，不再自动更新。
4. **版本对比**：在共享片段管理界面，可查看所有历史版本，进行左右分栏差异对比。

### 存储方案

**数据库存储 + SHA-256 哈希字段**（折中方案）：

- `shared_fragment_versions` 表存储内容 + `content_hash` 字段
- **始终计算 SHA-256**（成本可忽略，避免未来回填）
- 未来升级路径：新增对象存储层，新版本写入时同时存哈希指向对象

### 删除保护

如果源包要删除已被引用的共享片段，软件强制提示并建议转为各包私有副本，防止内容丢失。

⚠️ **风险点**：共享片段的版本管理增加数据库体积。虽然文本片段体积小，但需要定期清理过旧版本（如只保留最近 10 个版本）。

## 共享资源机制

**状态**：🟡 Phase 1（基本引用） / Phase 2（有效期/收藏/断裂修复）

### 场景

> 小李多个包都要展示同一个软件的截图。他将截图放入库的 `.shared/` 目录，在多个包中引用。他给重要的素材加了收藏，避免误删；给临时截图设置了 30 天有效期。

### 物理结构

```
我的工作空间/
  .shared/               ← 库级共享资源池（隐藏）
    screenshot.png
    common-template.docx
    tool.exe
```

### 资源元数据

数据库 `shared_resources` 表记录：

| 字段 | 说明 |
|------|------|
| id | 资源 UUID |
| relative_path | 相对于库根的路径 |
| content_hash | 内容指纹（SHA-256） |
| type | 资源类型（image/exe/doc 等） |
| expiry_date | 有效期（可选） |
| starred | 是否收藏保护 |

### 引用方式

包在 `.packmeta.json` 的 `resources` 数组中添加引用记录，指向资源 ID。

### 生命周期管理

- **有效期**：用户可为资源设置过期时间（如 exe 默认 1 年），到期后在"过期资源清理"中列出
- **收藏保护**：重要资源加星标收藏，被收藏的资源无法被普通清理删除

### 引用断裂修复

**基于内容哈希的自动匹配 + 手动修复兜底**：

1. **内容指纹**：资源首次添加时自动计算 SHA-256，通过软件修改时更新
2. **自动修复**：访问引用时发现路径失效 → 按哈希扫描 `.shared/` → 找到唯一匹配则自动恢复
3. **多匹配**：提示用户选择
4. **未找到**：标记为"缺失"，UI 显示 ⚠️ + [重新定位] [移除引用] [查看详情]
5. **惰性检测**：仅访问断裂引用时触发，启动时不全量扫描

### 库健康检查

提供"库健康检查"功能（`plugin-library-manager` 插件），扫描所有包的引用和 `.shared/` 实际文件，报告：
- 断裂的引用数量
- `.shared/` 中未被引用的文件（候选清理）
- 资源路径与数据库不一致的记录

⚠️ **风险点**：用户在文件管理器中直接修改了共享资源的内容（如编辑了图片），哈希变了，自动匹配会失败。这是合理行为——用户实质上替换了资源，应显式确认。

## 双链与引用解析

**状态**：🟡 Phase 1（包级） / Phase 2（片段级）

### 语法

- `[[包名]]`：链接到一个包，展示时进入包的阅读视图
- `[[包名|显示文本]]`：别名链接
- `[[包名#片段ID]]`：链接到包内某个具体片段

### 链接稳定性

- 包被移动或重命名时，内部 UUID 不变，所有双链自动保持有效
- 数据库维护包名 → UUID 的映射，渲染时动态解析

### 反向链接

库级 SQLite 维护反向链接，可查到"哪些包引用了当前包/片段"。

### 场景

> 小李在"游记"中写 `[[项目复盘]]` 链接到另一个包。点击链接后跳转到"项目复盘"包。在"项目复盘"的反向链接面板中，可以看到"游记"引用了它。

### Phase 1 详细方案（2026-07-12 确认）

#### 数据模型

**`packages` 表**（包注册表）：

| 字段 | 类型 | 说明 |
|------|------|------|
| `uuid` | TEXT PK | 包 UUID（来自 `.packmeta.json` 的 `id`） |
| `library_id` | INTEGER | 所属库 ID |
| `title` | TEXT | 包名（来自 `.packmeta.json` 的 `title`） |
| `dir_path` | TEXT | 包目录相对路径：`folder_id` 有值时相对**所属文件夹**，否则相对库根（库根直属包/旧数据） |
| `folder_id` | INTEGER | 包归属的注册文件夹 ID（v7 文件夹自治；NULL = 库根直属包） |
| `main_file` | TEXT | 主片段文件相对路径 |
| `created_at` | TEXT | 注册时间（ISO 8601） |
| `updated_at` | TEXT | 最后更新时间 |

索引：`(library_id, title)` 用于按名查找；`(library_id, dir_path)` 用于按路径查找。

**`links` 表**（双链索引）：

| 字段 | 类型 | 说明 |
|------|------|------|
| `source_package_uuid` | TEXT | 源包 UUID |
| `target_package_uuid` | TEXT | 目标包 UUID（未解析时为 NULL） |
| `target_name` | TEXT | 链接中原始的包名文本 |
| `display_text` | TEXT | 显示文本（`[[包名\|显示文本]]` 中的别名，无别名时同 `target_name`） |
| `source_file_path` | TEXT | 源文件相对路径（同一包内多文件可能都含链接） |
| `resolved` | BOOLEAN | 是否成功解析 |

主键：`(source_package_uuid, target_name, source_file_path)`

#### API 接口

| 方法 | 说明 |
|------|------|
| `searchPackages(library_id, query)` | 按包名模糊搜索，返回 `[{uuid, title, dir_path}]` 列表 |
| `getPackageByTitle(library_id, title)` | 精确匹配包名（D1：同名时返回第一个） |
| `getPackageByPath(library_id, dir_path)` | 按目录路径查找包 |
| `registerPackage(library_id, pkg)` | 注册或更新包信息（库扫描时调用） |
| `updatePackagePath(uuid, new_dir_path)` | 更新包路径（包被移动/重命名时） |
| `syncLinks(source_uuid, links[])` | 同步源包的所有双链（删除旧 + 插入新，事务原子） |
| `getBacklinks(target_uuid)` | 查询所有引用该目标包的源包列表 |
| `resolvePendingLinks(library_id)` | 重新解析 `resolved=false` 的链接（D3：包重命名后尝试匹配新名） |

#### markdown-it wikilink 插件

- 解析 `[[包名]]` 和 `[[包名|显示文本]]` 语法
- 渲染为 `<a class="wikilink" data-target="包名" data-resolved="true|false">显示文本或包名</a>`
- 未解析的链接追加 `unresolved` 类，UI 中以红色虚线样式 + tooltip "包不存在"显示（D2）

#### 自动补全（D5）

- **触发条件**：用户输入 `[[` 后再输入至少 1 个字符（非输入 `[[` 立即触发）
- 调用 `searchPackages(library_id, query)` 获取候选
- 显示下拉列表，最多 10 条，按相关度排序
- 选择后插入 `[[包名]]`（无别名）或用户按 Tab 补全 `[[包名|` 后输入别名

#### 保存时扫描流程

1. 用户保存文件时，正则扫描 `[[...]]` 提取所有链接
2. 调用 `syncLinks(source_uuid, links)` 更新数据库（事务原子）
3. 同时调用 `resolvePendingLinks` 尝试重新解析未解析项

#### 点击跳转

- 拦截 `.wikilink` 点击事件
- 通过 `data-target` 查询包 UUID
- emit `package:open` 事件，payload 含 `target_uuid` 与 `target_name`
- workspace 路由到对应容器打开包（如无对应容器则创建新容器）

#### 反向链接面板（D4）

- **位置**：侧边栏（独立容器，非编辑器底部）
- 显示当前打开包的所有反向链接
- 每条显示：源包名 + 引用上下文（链接前后各 30 字符）
- 点击反向链接条目跳转到源包对应位置

#### 实施步骤

```
Step 1: kmgr-core 数据模型 — packages 表 + links 表 + CRUD + 单元测试
Step 2: Tauri IPC + kmgr-api 封装 — 8 个 API 对应的 invoke 封装
Step 3: 包扫描注册 — 库扫描时全量注册（D6）
Step 4: markdown-it wikilink 插件 — 解析 + 渲染
Step 5: 保存时扫描 + syncLinks — markdown 插件集成
Step 6: 自动补全 — 编辑器内集成（D5: 至少 1 字符触发）
Step 7: 点击跳转 + 反向链接面板（D4: 侧边栏）
```

#### 决策点记录（2026-07-12 确认）

| # | 决策 | 选择 |
|---|------|------|
| D1 | 包名唯一性 | 建议唯一但不强制，同名时链接解析到第一个 |
| D2 | 未解析链接显示 | 红色虚线样式 + tooltip "包不存在" |
| D3 | 包重命名后旧链接 | 不自动更新源码，`resolvePendingLinks` 尝试匹配新名 |
| D4 | 反向链接面板位置 | 侧边栏（非编辑器底部） |
| D5 | 自动补全触发 | 输入至少 1 字符后触发（非输入 `[[` 立即触发） |
| D6 | 包注册时机 | 库扫描时全量注册 |

⚠️ **风险点**：
- R8：包被删除后，引用方的 `links` 表中 `target_package_uuid` 仍指向已删除包，UI 应优雅降级为"目标包不存在"提示，不应崩溃
- R9：用户在文件管理器中直接重命名 `.pack` 文件夹，下次库扫描时 `dir_path` 失效，需通过 UUID 匹配 `.packmeta.json` 中的 `id` 字段恢复（要求 `.packmeta.json` 中 `id` 始终存在且稳定）

## 文件与目录约定

### 文件夹命名与标识

| 类型 | 后缀 | 元数据文件 | 识别条件 |
|------|------|------------|----------|
| 项目 | `.proj` | `.projmeta.json` | 两个条件同时满足 |
| 包 | `.pack` | `.packmeta.json` | 两个条件同时满足 |

⚠️ **风险点**：`.pack` 后缀在 macOS 上无特殊含义（区别于 `.pkg` 安装包），但用户可能不熟悉。软件需要在 UI 中明确标注类型。

### 隐藏元数据文件

所有配置和索引文件（`.library.db`、`.projmeta.json`、`.packmeta.json`、`.shared/`）以点开头，并在 Windows 上额外设置隐藏属性。

### 向后兼容

扫描时同时识别：
- `.pack` 后缀文件夹 + `.packmeta.json`
- 含 `.packmeta.json` 的普通文件夹（平滑迁移）

## 用户体验分级

### 自动检测，无切换按钮

- **简单模式（默认）**：新用户每个包只有一个片段，界面像普通编辑器，隐藏多片段、共享块等概念
- **进阶模式（自动触发）**：用户尝试插入非 Markdown 内容（如 CSV 表格）或使用共享块时，自动进入多片段模式

### 设计原则

- 不显示"简单/进阶模式"标签
- 功能按需暴露
- 用户不需要理解"模式"概念

### 场景

> 小李刚开始使用，创建了一个包写游记。界面就是一个普通的 Markdown 编辑器。后来他想在游记中插入一个数据表，点击"插入表格"后，软件自动创建了一个 CSV 片段，追加到片段列表。小李看到的是表格出现在文档中间，并不需要理解"片段"的概念。

## 技术选型与限制

| 方面 | 选型 | 说明 |
|------|------|------|
| 数据库 | SQLite | 每个库一个文件，存储文本共享块、资源索引、双链关系、全文搜索 |
| 二进制文件 | 文件系统 | 绝对不存入数据库，保证备份和同步可靠性 |
| 哈希算法 | SHA-256 | 共享片段和共享资源统一使用 |
| 跨平台 | 隐藏文件 + Windows 隐藏属性 | 双保险，同步工具不遗漏元数据 |
| 多用户 | 单用户本地使用 | 未来如需协作，单独设计共享库机制 |

## 场景走查

**小李是一名自由职业者，用本软件管理自己的知识和工作。**

1. 他新建了一个库，命名为"我的工作空间"。
2. 他先建了一个项目 `设计案例.proj`。
3. 在这个项目里，他为每个客户案例创建了一个包，比如 `A公司品牌升级.pack`。
   - 最初这个包是简单模式，只有一个 `A公司品牌升级.md` 和若干附件。
4. 后来他想把"设计流程"单独做成一个可复用的章节，于是选中那些文字，右键"发布为共享片段"，起名为"通用设计流程"。
5. 在另一个包 `B公司宣传册.pack` 中，他输入 `[[通用设计`，搜索并插入了该共享片段。
6. 几周后，他优化了通用设计流程，所有引用它的包都自动更新了。其中 B 公司的项目主管要求保持旧版，他就对该引用锁定了版本。
7. 他收集了一些常用设计素材图片，放入库的 `.shared/` 文件夹，并在相关包中引用它们。他给重要的素材加了收藏，避免误删；给临时截图设置了 30 天有效期。
8. 最终，他将 `A公司品牌升级.pack` 导出为精美的 PDF，使用了自定义 CSS 样式，直接发送给客户。

## 讨论记录

### 2026-07-12 初次讨论

**参与方**：用户 + AI

**讨论内容**：
1. 用户提出"包"的初步定义：内容不可分割的一组内容（如 markdown + 图片）
2. 用户提出"格式变体"概念：同一内容的不同格式（如 markdown + pdf），内容应一致
3. 用户区分"包"与"项目"：项目是主题聚合，文件相互独立
4. AI 评估：定义准确，建议区分"依赖资源"和"格式变体"两个层次
5. AI 建议共享资源用"资源池 + 引用关系"方案，格式同步用"stale 标记 + 手动刷新"

**已确定**：
- 包的定义：内容不可分割的完整单元
- 共享资源处理：共享资源池 + 引用关系
- 格式变体同步：stale 标记 + 手动刷新
- 格式变体与依赖资源的区分：变体可删除/重新生成，依赖资源不可分割
