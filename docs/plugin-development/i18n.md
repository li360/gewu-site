# GeWu 国际化（i18n）规范

> 状态：**规范先行，存量文案未迁移**。本规范定义新代码的国际化写法、语言文件格式与志愿者翻译流程；存量中文文案的迁移按文末路线图推进。

## 1. 背景与目标

GeWu 目前全部 UI 文案为硬编码中文（主壳 + 20+ 插件 + Rust 错误消息）。为支持多语言（首批目标：英文）并允许志愿者参与翻译，采用**自建轻量 i18n 方案**：

- 无第三方依赖，核心为 `workspace` 包内一个纯逻辑模块 + React Context 封装
- 语言文件为**纯 JSON**（对志愿者友好，可直接被翻译平台/人工编辑）
- 支持 `{var}` 插值、点路径键、多级回退（当前语言 → 回退语言 → 键本身）

## 2. 核心模块

位于 `packages/workspace/src/i18n/`，从 `workspace` 包统一导出：

| 导出 | 说明 |
|------|------|
| `createI18n(options)` | 纯逻辑工厂（无 React 依赖），返回 `t` / `getLang` / `setLang` / `getLanguages` |
| `<I18nProvider options>` | React 提供者，包在应用根部 |
| `useI18n()` | Hook，返回 `{ t, lang, setLang, languages }` |

### createI18n 选项

| 选项 | 默认 | 说明 |
|------|------|------|
| `resources` | 必填 | `{ 语言代码: 字典 }`，如 `{ "zh-CN": zhCN, "en": en }` |
| `initialLang` | `"auto"` | `"auto"` 时依次从 localStorage → `navigator.language` 检测，否则为明确语言代码 |
| `fallbackLang` | `"zh-CN"` | 缺失键时的回退语言；不存在则取第一个可用语言 |
| `storageKey` | 无 | 语言选择持久化键名（沿用 `gewu-*` 命名，如 `gewu-lang`） |

### 语言匹配规则

- 精确匹配（大小写不敏感，`zh_CN` 视为 `zh-cn`）
- 前缀匹配：`zh` → `zh-CN`；`en` → `en-US` 等
- 均不匹配 → 回退语言

## 3. 使用方式

### 3.1 应用根接入（未来由 ui-framework 的 App.tsx 完成）

```tsx
import { I18nProvider } from "workspace"
import zhCN from "workspace/src/i18n/locales/zh-CN.json"
import en from "workspace/src/i18n/locales/en.json"

<I18nProvider resources={{ "zh-CN": zhCN, en }} storageKey="gewu-lang">
  <App />
</I18nProvider>
```

> 语言文件在 `packages/workspace/src/i18n/locales/<语言代码>.json`。接入方 import JSON 时需在自身 tsconfig 开启 `resolveJsonModule`（Vite 无需配置）。

### 3.2 组件内使用

```tsx
import { useI18n } from "workspace"

function SaveButton() {
  const { t, lang, setLang } = useI18n()
  return <button title={t("common.save")}>{t("common.ok")}</button>
}
```

带插值：

```tsx
t("common.confirmDelete", { name: file.name }) // "确定要删除「a.md」吗？"
```

## 4. 键命名规范

- **点路径**：`命名空间.段落.动词`，如 `common.ok`、`file-list.title`、`settings.tabs.general`
- **插件**：插件以自身 `pluginId` 作为一级命名空间（如 `webview.nav.back`、`export.dialog.title`），避免合并各插件语言文件时冲突
- **键必须语义化、稳定**：键是"含义"不是"译文"，翻译变更不修改键；键缺失时界面回退显示键本身，便于发现漏译
- **插值参数**：用 `{name}` 形式，参数名语义化；同一键的参数不得改名（会影响所有语言）

## 5. 语言文件

- 位置：`<包>/src/i18n/locales/<语言代码>.json`（语言代码见 [BCP 47](https://www.rfc-editor.org/rfc/bcp47)，如 `zh-CN`、`en`、`ja`）
- `zh-CN.json` 为**主语言**（事实标准），新增键必须先加到 zh-CN，再补其他语言
- 各语言文件的**键集合必须与 zh-CN 一致**（漏键/多余键均视为错误；CI 校验脚本待建）
- JSON 键与结构约定见第 4 节

## 6. 插件接入规范（新插件 / 新代码必须遵守）

1. 插件包内新增 `src/i18n/locales/<语言代码>.json`，一级命名空间用插件 `pluginId`
2. 插件组件用 `useI18n()` 获取 `t`，不再硬编码中文 UI 文案
3. 插件不自行创建 I18nProvider，统一使用应用根挂载的实例（应用根需合并插件语言文件：`resources = { lang: { ...框架字典, ...插件字典 } }`，一级命名空间天然隔离）
4. 命令面板、菜单、右键菜单等注册项中面向用户的 `label` 同样必须走 `t()`

> 插件语言文件合并与自动扫描机制（从各插件 `locales/` 目录收集）将在存量迁移阶段实现；当前以根级合并为准。

## 7. 志愿者翻译流程

**前提约束**：GeWu 源码不公开，仅发布编译产物。为让志愿者参与翻译，语言文件将**单独开放**：

1. `packages/*/src/i18n/locales/*.json` 定期同步到公开翻译仓库（如 Gitee/GitHub 上的 `gewu-i18n` 仓库，或接入 Weblate/Crowdin 等翻译平台）
2. 志愿者直接编辑 JSON（保持键集合与 `zh-CN.json` 一致），或以平台在线翻译
3. 合回：主项目定期拉取翻译仓库 → 校验键集合一致 → 随发版打包进应用
4. 新增语言：提交 `ja.json` 等新文件即自动进入构建资源

**对翻译者的要求**：
- 不增删键、不改键名，只改值
- 保持 `{var}` 占位符不变
- 新增语言文件必须包含与 `zh-CN.json` 相同的全部键

## 8. Rust 端错误消息（迁移阶段执行）

Rust（`kmgr-core` / `tauri-app`）返回给前端的错误目前为硬编码中文（如"知识库未打开"）。迁移规范：

- Rust 端错误改为**错误码或错误键**（如 `KB_NOT_OPEN`），不再返回中文文案
- 前端 `invoke` 封装层将错误码映射为 `t("errors.kb_not_open")`，随语言切换显示
- 期间新增的 Rust 错误消息一律使用错误码 + 英文默认文案，不新增中文文案
